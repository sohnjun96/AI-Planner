# 플래나이 질문 기능 재설계안

2026년 10월 3일 기준 소스 검토와 제안이다. 현재 구현, 권장 설계, 합성 예시를 구분해 기술했다. 이 문서와 함께 제시하는 결과 화면은 기획용이며 앱의 질문 기능을 변경한 것은 아니다.

질문 기능을 **내 기록을 조회하고, 근거를 확인하고, 필요한 결과물을 만드는 작업 공간**으로 바꾸는 것을 권한다. 조회 조건과 숫자는 앱이 책임지고, AI는 질문을 해석하고 자료를 설명한다. 핵심은 질문창을 크게 만드는 데서 끝내지 않고 조회 방식, 근거 연결, 후속 질문, 결과 저장을 함께 바꾸는 것이다.

사용자가 제시한 `분류 예산 출장 언제 갔었지?`, `저번 AI 활용 교육 관련 노트 찾아봐줘`를 핵심 사례로 삼는다. 첫 구현의 우선순위는 **기억나는 업무 주제와 상황을 단서로 과거 일정·노트를 찾는 경험**이다. 짧은 날짜 답변과 원래 기록, 관련 노트 목록이 먼저 나오고, 집계나 보고서 작성은 그 자료를 확인한 뒤 이어지는 활용으로 둔다.

## 현재 조회 방식

현재는 상단 질문 버튼에서 모달을 열어 질문 하나를 입력한다. 앱이 보유한 일정·노트 배열을 AI 에이전트에 넘기지만, 배열 전체의 본문을 최초 요청에 보내는 방식은 아니다.

```text
상단 질문 버튼
  → 질문 모달
  → 질문 + 현재 시각 + 프로젝트 목록 + 제목 카탈로그를 LLM에 전달
  → 모델이 JSON으로 조회 도구와 인자를 반환
  → 앱이 로컬 배열에서 조회
  → 조회 결과를 첨부해 LLM에 다시 요청
  → 답변 Markdown + 참고 항목 + 도구 호출 요약 표시
```

| 단계 | 실제 구현 | 사용자에게 미치는 영향 |
| --- | --- | --- |
| 데이터 공급 | AppDataContext에서 IndexedDB 자료를 읽는다. 일정은 시작 시각순 최대 20,000건, 노트는 최근 수정순 최대 10,000건을 로드한다 | QA는 DB 전체에 직접 질의하지 않고 전달받은 배열 안에서 조회한다. 공급 한도를 넘으면 조회에서 누락될 수 있다 |
| 최초 카탈로그 | 보관하지 않은 노트 중 최근 수정순 제목 최대 80개, 현재 시각과 가까운 일정 제목 최대 100개, 프로젝트 ID·이름 | 질문과 무관한 제목도 서버에 전달된다. 카탈로그 밖의 자료는 추가 검색에 의존한다 |
| 조회 지시 | 일반 Chat Completions의 텍스트 응답에서 JSON `toolCalls`를 읽는다 | 네이티브 function calling을 요구하지 않아 현재의 모델 호환성을 유지한다 |
| 조회 도구 | `search_notes`, `get_note`, `search_tasks`, `get_task` 네 가지 | 루틴, 일별 메모, 노트 버전, 연결 관계 전용 조회는 QA가 호출할 수 없다 |
| 반복 한도 | 논리적 LLM 라운드 3회, 라운드당 도구 최대 2개. 마지막 라운드는 추가 조회를 실행하지 않는다 | 실제 조회는 최대 4회다. 검색→본문 확인→관계 확장처럼 여러 단계가 필요한 질문은 자료가 부족해질 수 있다 |
| 형식 복구 | JSON 파싱 실패 시 해당 요청을 한 번 더 보낸다 | 논리적 라운드 3회와 HTTP 요청 3회는 같은 뜻이 아니다 |
| 최종 출력 | 답변 문자열, 최대 8개의 참고 항목, 도구 호출 횟수 요약 | 답변 종류별 표현, 전체 집계, 문장별 근거 연결이 없다 |

구현 근거는 `src/components/AskDataModal.tsx:43`, `src/agent/qaAgent.ts:76`, `:108`, `:128`, `:151`, `:172`, `src/agent/agentUtils.ts:200`, `src/context/AppDataContext.tsx:190`, `:769`이다.

### 일정과 노트를 실제로 검색하는 방법

일정 검색은 제목·본문·프로젝트 이름과 설명·일정 종류 이름을 이어 붙인 문자열에 검색어가 포함됐는지 검사한다. 소문자 변환과 앞뒤 공백 제거를 하고, 날짜·상태·프로젝트 조건은 모두 만족해야 한다. 날짜 조건이 있으면 일정 시작 시각순, 없으면 최근 수정순이다.

노트 검색은 제목·본문·태그·프로젝트 이름에 대해 같은 포함 검사를 한다. 프로젝트·상태·태그 조건을 지원하고 최근 수정순으로 정렬한다. 태그 조건은 실행기에 있으나 QA 프롬프트의 도구 설명에는 없다.

두 검색 모두 기본 15건, 최대 30건만 반환한다. 다중 검색어의 AND·OR 구분, 관련도 순위, 동의어 처리, 총 검색 건수, 다음 페이지가 없다. 예를 들어 본문에 `교육 실적 취합`만 있으면 `교육 결과 모으기`라는 검색어로는 잡히지 않을 수 있다.

해석하지 못한 날짜·상태 조건은 경고를 붙이고 무시하므로 의도보다 넓은 범위를 조회할 수 있다. 날짜 검사는 문자열 형식 중심이며 실제로 존재하는 날짜나 시작일·종료일 순서를 충분히 검증하지 않는다. 재설계에서는 잘못된 조건을 조용히 제거하지 않고 수정 가능한 오류로 돌려준다.

| 내용 | 현재 전달 길이 | 놓칠 수 있는 정보 |
| --- | --- | --- |
| 일정 검색 결과 본문 | 앞 160자 | 긴 본문 뒤의 장소·준비사항 |
| 일정 상세 조회 본문 | 앞 500자 | 뒤쪽의 세부 조건 |
| 노트 검색 발췌 | 앞 200자 | 실제 검색어가 본문 뒤에 있으면 발췌에 나타나지 않음 |
| 노트 상세 본문 | 앞 4,000자 | 긴 회의록 뒤의 결정사항. 잘림 여부는 전달됨 |
| 누적 도구 결과 | 결과 본문 직렬화 기준 약 12,000자 예산 | 일부 자료가 축약·생략될 수 있음 |

일정 날짜 필터는 **시작일**만 본다. 종료일이 있는 일정이 검색 기간과 겹치는지, 언제 완료했는지에 대한 조회가 아니다. `completedAt`은 원래 Task 모델에 있지만 QA 도구 결과에는 포함되지 않는다. 현재 시각은 UTC ISO 문자열로 보내고, 검색 날짜는 브라우저 로컬 날짜로 계산하므로 질문 기준 시간대를 명시할 필요가 있다.

노트 최초 카탈로그는 보관 노트를 제외하지만 `search_notes`는 상태를 지정하지 않으면 보관 노트도 검색한다. 따라서 질문의 기본 자료 범위도 일관되지 않다. 근거는 `src/agent/agentTools.ts:27`, `:126`, `:207`, `:289`, `:340`, `src/models.ts:53`이다.

### 답변과 근거를 확인하는 방법

모델이 낸 참고 ID가 전달된 전체 노트·일정 배열 안에 존재하는지 확인하고, 제목은 앱의 실제 제목으로 교체한다. 그러나 해당 자료를 이번 질문에서 조회했는지, 그 자료의 어느 부분이 답변을 뒷받침하는지는 검사하지 않는다. 제목 카탈로그만 보고 바로 답변하는 것도 허용한다.

따라서 존재하지 않는 참고 ID를 상당 부분 걸러낼 수는 있어도, **본문을 확인하지 않은 결론이나 근거와 맞지 않는 문장까지 검증하는 구조는 아니다.** JSON 파싱이 두 번 실패하면 원문 일부가 근거 없는 답변으로 표시될 수도 있다. 근거는 `src/agent/qaAgent.ts:92`, `:217`, `:261`이다.

현재 모달은 매 질문 때 답변을 초기화하고 이전 대화를 보내지 않는다. 근거를 클릭하면 모달을 닫고 원래 화면으로 이동하므로 답변이 사라진다. 질문 기록, 답변 복사, 노트 저장, 중지 버튼, 범위 선택이 없다. 근거는 `src/components/AskDataModal.tsx:24`, `:50`, `:85`, `:169`이다.

| 문제 | 개선 방향 |
| --- | --- |
| 모델이 검색어와 조회 순서를 전부 결정 | 먼저 검증 가능한 조회 계획을 만들고 앱이 조건을 실행 |
| 최대 30건의 일부 결과로 전체 현황을 설명할 가능성 | 전체 집계와 화면에 보여 줄 목록을 분리. 전체 건수·표시 건수·누락 이유를 함께 반환 |
| 본문 앞부분만 전송 | 검색어가 나온 문단을 발췌하고, 필요할 때 해당 부분을 추가 조회 |

| 모달을 닫으면 맥락 소실 | 전용 질문 화면과 세션 상태로 질문·결과·범위를 보존 |
| 질문마다 긴 글로 답변 | 찾기에는 목록, 상태 비교에는 표, 집계에는 수치, 변화에는 타임라인 사용 |
| 기록이 없다는 것을 실제 업무 미수행으로 해석할 위험 | 자료 미발견·처리 여부 미확인·검색 불완전 상태를 구분 |

## 질문 기능의 역할과 진입점

상단의 `질문` 버튼은 유지하고 `#/questions` 전용 화면으로 연결한다. 대시보드·나의 루틴·노트·프로젝트·나의 기록의 다섯 메뉴는 유지한다. 별도 메뉴를 하나 더 늘리는 대신 질문 버튼의 활성 상태와 화면 제목으로 현재 위치를 알린다.

프로젝트 상세에는 `이 프로젝트에 질문`, 노트에는 `이 노트에 질문`, 일정에는 `관련 기록 확인`을 제공한다. 진입할 때 선택한 범위를 입력창 위에 표시하고 사용자가 바로 바꿀 수 있게 한다. 현재 보고 있는 프로젝트라고 해서 전체 질문을 조용히 제한하지 않는다.

질문과 AI 일정 기능은 연결하되 각 역할은 구분한다. 질문은 자료 확인과 결과 작성, AI 일정은 생성·수정·삭제 초안 검토를 담당한다. 답변에서 `일정 초안 만들기`를 누르면 기존 검토 흐름으로 전달한다. 초기 재설계에서는 질문 답변이 일정이나 노트를 자동으로 수정하지 않는다.

## 질문 종류와 활용 예시

다음 두 질문은 사용자가 제공한 예상 사용 사례다. 실제 기록을 조회한 결과는 아니며 아래의 응답 표현은 화면 설계용이다.

### 기억나는 단서로 과거 기록 찾기

| 사용자 질문 | 해석할 의도 | 조회와 확인 | 기본 결과 |
| --- | --- | --- | --- |
| 분류 예산 출장 언제 갔었지? | 기억나는 업무 단서로 과거 출장 날짜 확인 | 출장 종류, 과거 일정, 제목·본문·프로젝트의 관련 단서를 대조하고 필요한 연결 노트를 확인 | 기록상 출장 기간을 짧게 답하고 가장 관련 있는 일정 카드와 다른 후보 표시 |
| 저번 AI 활용 교육 관련 노트 찾아봐줘 | 이전 관련 교육과 그 자료 찾기 | AI 활용·교육에 관련된 노트를 찾고 원문 교육일이나 연결 일정으로 행사 후보를 구분 | 관련 노트 제목·매칭 문단·교육일·수정일과 원문 열기 |

`분류 예산`은 사용자가 기억하는 표현으로 보존한다. 이를 특정 프로젝트명이나 출장 목적이라고 임의 확정하지 않는다. `예산`이 예산 편성 업무인지 지명인지도 원문 확인 전에는 정하지 않는다. `분류`, `예산`을 검색 단서로 삼아 같은 기록 안에서 함께 확인되는 후보를 우선한다. `출장`은 기존 일정 종류에서 먼저 확인하고 제목·본문의 출장 표현도 관련 후보 탐색에 사용한다. `언제 갔었지`는 본문 검색어에서 제외해 과거 날짜를 확인하려는 의도로 처리한다.

제목이 `분류 업무 예산 협의`처럼 단서 사이에 다른 말이 있어도 찾을 수 있어야 한다. 따라서 사용자 질문 전체를 하나의 문자열로 검색하지 않는다. 제목·본문·프로젝트에서 단서를 각각 찾고 일치 위치를 표시한다. 두 단서가 모두 있는 후보가 없으면 한 단서만 맞는 자료나 관련 표현을 찾되, `예산 단서는 확인했으나 분류 관련 여부는 확인 필요`처럼 빠진 조건을 드러낸다. 검색 조건을 조용히 제거해 부분 일치 후보를 정답으로 표시하지 않는다.

출장은 날짜와 방문 사실을 구분한다. `startAt`·`endAt`은 기록된 출장 기간의 근거이며, 날짜가 과거이거나 일정이 완료 상태라는 이유만으로 실제 다녀왔음을 증명하지 않는다. 취소 일정은 기본 후보에서 제외하고, 과거 미완료·보류 일정도 놓치지 않되 `등록된 출장 일정이며 방문 여부 미확인`으로 표시한다. 연결 노트에 방문·참석 내용이 명시돼 있으면 그 기록을 추가 근거로 보여 준다. 가장 관련 있는 출장과 가장 최근 출장의 날짜가 다르면 관련도와 행사 시점을 함께 표시한다.

`저번`은 특정 한 달이나 최신 수정일을 뜻한다고 고정하지 않는다. 관련 교육의 원문 날짜 또는 연결 일정의 행사일을 기준으로 이전 행사를 찾는다. 예전 교육 노트를 최근에 편집했다고 해서 최근 교육으로 간주하지 않는다. AI 활용과 관련된 표현을 넓혀 후보를 찾더라도 실제 내용이 교육에 관한 것인지 확인하고, AI 일반 메모나 교육 일정만 적힌 노트와 구분한다.

교육일이 확인된 경우 행사별로 관련 노트를 묶고, 명확한 날짜가 없으면 `교육일 미확인`이라고 표시한다. 교육 노트가 둘 이상이면 우선 관련 후보를 보여 준다. 사용자가 날짜·장소·기관·주제 중 하나를 추가하면 그 후보 안에서 다시 좁힌다. 처음부터 사용자가 정확한 명칭이나 날짜를 알아야만 검색할 수 있게 만들지 않는다.

| 상황 | 적절한 표현 |
| --- | --- |
| 출장 일정 한 건이 명확히 일치 | 기록상 관련 출장 일정은 `[시작일]–[종료일]`입니다. 제목과 날짜의 근거를 함께 표시 |
| 관련 출장 여러 건 | 관련 출장 후보를 찾았습니다. 각 후보의 날짜·일치한 업무 단서·상태를 나란히 표시 |
| 방문 사실까지 확인되지 않음 | 등록된 출장 기간입니다. 실제 방문 여부는 기록에서 확인하지 못했습니다 |
| 교육 노트 여러 건 | 관련 노트를 찾았습니다. 행사일이 확인된 묶음과 날짜가 없는 노트를 구분해 표시 |
| 본문 단서 일부만 일치 | 일치한 단서와 아직 확인하지 못한 단서를 표시하고 원문 확인으로 연결 |

결과의 첫 행동은 `일정 열기` 또는 `노트 열기`다. 출장이면 필요할 때 `그 출장 관련 노트`, 교육이면 `그 교육 일정도 보여줘`, `교육 내용만 요약해줘`로 이어진다. 초안 저장이나 보고서 버튼은 이 질문들의 기본 결과를 차지하지 않도록 보조 행동으로 둔다.

3. `9월에 완료한 일 집계해줘` → `프로젝트별로` → 완료일이 없는 기록을 별도 확인 → 보고서 초안을 만든다.

## 조회 구조의 재설계

```text
질문과 이전 맥락
  → 의도·대상·기간·날짜 기준·기억 단서 해석
  → 타입과 허용 범위를 검증한 조회 계획
  → 로컬 저장소에서 필터·검색·전체 집계
  → 필요한 연결 자료와 본문 문단 조회
  → 조회 범위·누락·근거 묶음 확정
  → AI 설명과 유형별 구조화 결과 생성
  → 근거·숫자·출력 형식 검사
  → 결과 화면 / 후속 질문 / 결과물 초안
```

### 조회 계획을 먼저 확정

AI는 `의도`, `자료 종류`, `프로젝트`, `기간`, `날짜 기준`, `상태`, `검색 표현`, `결과 형태`를 구조화해 제안한다. 앱은 ID, 실제 달력 날짜, 기간 순서, 허용 연산을 확인한다. 자유로운 SQL·JavaScript를 생성해 실행하는 구조는 사용하지 않는다.

기억을 되찾는 질문에서는 확실한 조건과 추정한 단서를 구분한다. `출장`과 `노트 찾아줘`는 자료 종류를 정하는 단서이고, `분류 예산`과 `AI 활용 교육`은 원문을 보존한 검색 단서다. `저번`은 관련 행사 후보를 찾은 뒤 시점을 비교하는 조건이다. 단서에 없는 프로젝트 ID, 교육 기관, 월 범위를 만들어 검색을 제한하지 않는다.

`다음 주 제출 일정 중 미완료`는 앱이 날짜 범위를 정하고 종류 ID와 상태를 해석할 수 있다. 프로젝트 이름이 둘 이상 일치하거나 `완료 실적`과 `예정 업무 완료율` 중 무엇인지 결과가 크게 달라지는 경우에만 짧은 선택지를 보여 준다. 해석이 분명한 질문은 바로 실행하고, 해석한 조건을 결과 위에 표시한다.

상대 날짜는 `now`, `timezone`, `today`, `weekStartsOn`을 한 기준 시점에서 계산한다. 권장 운영 기준은 Asia/Seoul이며 앱의 기존 날짜 표시와 함께 검증한다. `이번 주`는 앱 설정의 주 시작일을 따르고 실제 날짜 범위를 항상 보여 준다.

### 정확한 조건 조회와 본문 검색을 분리

날짜·상태·프로젝트·종류·중요도는 로컬 데이터 필드로 조회한다. 전체 건수와 집계는 화면 목록의 30건 제한에 영향을 받지 않아야 한다. 현재 AppDataContext 배열의 한도에도 의존하지 않도록 별도 조회 저장소를 두고 IndexedDB를 직접 질의한다.

본문 검색은 우선 로컬에서 제목·태그·본문의 토큰 일치, 문구 일치, 제한된 동의어 확장을 조합한다. 제목과 태그의 정확한 일치를 높게 평가하고, 최신 수정일은 동점 처리에 보조적으로 사용한다. 한글 조사·띄어쓰기·약어·이름 표기 차이는 실제 질문 세트로 검증한 범위에서 처리한다. 동의어가 같다는 이유로 사람이나 프로젝트를 자동 병합하지 않는다.

검색용 텍스트와 문단 위치를 별도 색인으로 만들면 긴 노트도 매칭 위치를 중심으로 읽을 수 있다. 색인은 원본 ID·수정 시각·버전으로 무효화하며 수정·삭제·백업 복원 후 재생성한다. 처음에는 현재 자료 규모에서 로컬 검색을 측정하고, UI가 멈추면 검색 계산을 Worker로 옮긴다.

의미 검색은 2차 확장으로 둔다. 로컬 어휘 검색으로 놓치는 질문이 실제로 많을 때 임베딩을 평가한다. 내부망에서 사용할 모델, 색인 생성 시간·용량, 한국어 검색 품질, 외부 전송 허용 범위를 확인한 뒤 추가한다. 일정의 날짜와 집계는 의미 검색을 추가해도 정확한 필드 조회를 계속 사용한다.

Dexie는 복합 인덱스와 범위 조회를 지원하므로 필요한 질의를 측정해 인덱스를 추가할 수 있다. 다만 복잡한 필터의 `count()`는 항목 순회가 필요할 수 있어 전체 집계가 항상 빠르다고 가정하면 안 된다. [Dexie 복합 인덱스](https://dexie.org/docs/Compound-Index), [Collection count](https://dexie.org/docs/Collection/Collection.count()).

### 단서 조합 검색의 실행 방법

아래는 제안하는 조회 계약이다. 현재 도구 API나 이미 구현된 동작을 나타내는 코드는 아니다. AI가 질문을 계약으로 바꾸면 앱이 허용된 값과 실제 ID를 검사한 뒤 실행한다.

```json
{
  "intent": "find_past_event_date",
  "sources": ["task"],
  "requiredScope": { "projectIds": [], "dateRange": null },
  "eventHint": { "kind": "출장", "time": "past" },
  "clues": ["분류", "예산"],
  "firstMatch": "all",
  "fallbackMatch": "any",
  "requestedFields": ["startAt", "endAt"]
}
```

`requiredScope`는 사용자가 지정한 프로젝트·기간 같은 반드시 지켜야 할 범위다. `eventHint`는 행사 종류와 시점의 해석이고, `clues`는 원문 검색 단서다. 프로젝트 배열이 비어 있으면 특정 프로젝트를 지정하지 않았다는 뜻이다. 출장 종류와 과거 시점을 우선 사용하고, 종류가 잘못 분류된 자료까지 찾아야 할 때는 제목·본문의 출장 표현을 확인하는 별도 후보 조회를 실행한다. 범위 제한은 이 과정에서도 유지한다.

앱은 일정의 제목·본문·종류 이름과 노트의 제목·본문·태그를 따로 검색한다. 같은 단어라도 제목에 있는지 본문에 있는지 구분하고, 원문 위치를 남긴다. 대소문자·공백·유니코드를 정리한 검색용 표현과 원문 사이의 위치 대응을 유지해 실제 발췌가 어긋나지 않게 한다. 초기에는 여러 단어의 각각의 일치를 조합하는 방식으로 구현할 수 있고, 한글 형태소 처리와 복잡한 의미 유사도는 별도로 평가한다.

첫 검색은 각 단서가 모두 확인되는 기록을 찾는다. `분류 AND 예산`은 두 단어가 연속해 있어야 한다는 뜻이 아니며, 같은 기록의 제목과 본문에서 각각 발견돼도 후보로 삼는다. 정확한 `분류 예산` 문구가 있는 기록은 더 높은 순위로 둘 수 있다. 프로젝트의 공통 설명에만 있는 단서는 약한 맥락으로 취급한다. 공통 설명에 두 단어가 있다는 이유로 프로젝트의 모든 일정을 직접 일치로 분류하지 않는다.

전체 단서 일치가 없으면 출장 단서는 유지하며 `분류 OR 예산`으로 부분 일치 후보를 찾는다. `모두 일치한 기록 없음, 일부 단서만 일치한 후보`라고 표시한다. 표현 확장은 원래 표현의 띄어쓰기 변형이나 검토된 별칭을 우선한다. AI가 제안한 유사 표현은 추가 후보 탐색에만 쓰고 원래 단서를 충족한 것으로 계산하지 않는다. 전혀 다른 표현으로 쓰인 기록은 이 최소 검색 방식에서 놓칠 수 있다.

### 후보 순위를 계산하고 원문으로 판별

처음에는 수치 점수보다 다음 기준을 순서대로 적용하는 정렬 규칙을 권한다. 순위는 관련 후보의 표시 순서이며 정답 확률이 아니다.

1. 원래 단서가 해당 기록의 제목·본문·태그에서 모두 확인되는지 먼저 본다.
2. 정확한 문구 일치, 제목·태그에 맞은 단서 수, 같은 문단에서 단서가 함께 나오는지를 비교한다.
3. 프로젝트 공통 설명만의 일치나 확장 표현만의 일치는 낮은 순위의 관련 후보로 둔다.
4. `언제 갔었지`는 관련도 이후 행사 날짜를 비교하고, `저번 교육`은 관련 교육 후보의 행사일을 확인한 뒤 가장 최근의 과거 행사를 우선한다. 노트 수정일로 행사일을 대체하지 않는다.

검색어의 위치·문서 필드·서로 가까운 정도를 관련도에 사용하는 원리는 일반적인 전문 검색에도 쓰인다. 여기서는 그 원리를 기존 로컬 자료에 적용하는 설계로 제안하며 별도 데이터베이스 도입을 전제로 하지 않는다. [PostgreSQL 검색 순위와 발췌 문서](https://www.postgresql.org/docs/current/textsearch-controls.html#TEXTSEARCH-RANKING).

| 합성 후보 | 검색 판별 | 초기 표시 순서 |
| --- | --- | --- |
| 출장 A 제목에 분류·예산 모두 있음 | 해당 기록에서 원래 단서 전체 일치, 제목에서 두 단서 확인 | 우선 후보 |
| 출장 B 제목에 예산, 본문에 분류 있음 | 해당 기록에서 원래 단서 전체 일치, 본문 확인 필요 | 다음 후보 |
| 출장 C에 예산만 있음 | 부분 일치, 분류 관련 여부 미확인 | 부분 일치 후보로 구분 |

이 순위만으로 A를 정답으로 확정하지 않는다. 예를 들어 A가 예산 편성 계획이고 B가 예산 지역 방문이면 사용자가 찾는 행사가 달라질 수 있다. 원문 확인 단계에서 이 차이를 설명하고, 질문의 정보만으로 하나를 정할 수 없으면 후보를 나란히 보여 준다.

### 원문 확인과 근거 발급의 실행 방법

검색 결과에는 원본 자료 종류·ID·수정 시각, 일치한 단서와 필드, 원문 문단 또는 위치 범위를 포함한다. 앱은 선택한 후보를 로컬 저장소에서 다시 읽고 검색 색인의 수정 시각과 대조한다. 다르면 최신 원문으로 다시 검색한다. 확인된 근거 묶음은 답변 생성 중 같은 스냅샷으로 사용하고 이후 수정은 별도 변화로 표시한다.

본문은 제목·소제목·문단 단위로 나누고 단서가 나온 문단과 필요한 앞뒤 문맥을 읽는다. 취소·부정 표현, 날짜가 다른 행사, 인용한 다른 사람의 기록을 이해할 수 있도록 단어가 나온 문장만 고립시키지 않는다. 초기 예산은 상위 후보 5개와 후보별 핵심 문단 2~3개 정도로 시작해 실제 모델의 응답 시간과 자료 길이로 조정한다. 더 읽을 자료가 있으면 추가 조회를 실행하고 못 읽은 범위를 남긴다.

출장 날짜는 일정의 원래 시작·종료 필드에서 가져온다. 실제 방문 여부는 방문·참석 문단이 있는지 별도로 읽는다. 교육 노트는 교육일이 명시된 문단이나 해당 교육과의 관계가 확인되는 연결 일정에서 행사일을 확인한다. 원문에 없는 연도·장소·참석 사실을 채워 넣지 않는다.

AI에 전달할 자료는 이 후보의 실제 발췌와 필드, 원문에서 앱이 발급한 근거 키다. AI는 `직접 관련`, `일부 관련`, `판단 불가`를 구분하고 뒷받침하는 근거 키를 선택한다. 앱은 인용 키·조회 범위·원문 발췌·날짜 필드를 검증한다. 발췌가 존재한다는 검증과 AI가 문맥을 올바르게 해석했는지는 서로 다른 검증이므로, 애매한 의미 판단은 후보 선택이나 확인 필요 상태로 남긴다.

노트 찾기 질문은 확인된 노트 목록과 원문 발췌까지만 반환해도 완료할 수 있다. 그다음 사용자가 요약을 요청하면 확인된 자료를 사용해 설명을 만든다. 원문에 없는 답을 생성하는 단계를 검색 성공으로 취급하지 않는다.

### 전체 집계와 설명용 근거를 분리

조회 결과는 최소한 `전체 대상 수`, `표시 항목 수`, `다음 페이지`, `전체 조회 완료 여부`, `적용 조건`, `조회 기준 시각`, `누락 이유`를 포함한다. 정확한 숫자는 앱에서 계산한 집계 객체로 렌더링하고 AI가 숫자를 다시 만들어 내지 않게 한다.

화면에 15행만 표시해도 전체 대상 120건을 집계할 수 있어야 한다. 검색 후보 제한·시간 초과·원본 잘림이 있으면 조회 범위가 불완전하다고 표시한다. 의미 검색 상위 후보만 읽은 상태에서는 `관련 자료 5건을 확인함`이라고 표현하고 `전체 자료에 없음`이라고 확정하지 않는다.

### 연결 관계를 활용

일정과 노트의 명시적 연결을 우선 사용하고 같은 프로젝트, 제목, 시간 근접성은 관련 후보를 찾는 데 사용한다. 유사한 제목만으로 `이 결정사항은 완료됐다`고 결론 내리지 않는다.

현재 연결은 노트 전체와 일정 사이의 연결이다. 회의록에 결정사항 세 개와 연결 일정 두 개가 있어도 어느 항목에 해당하는지 확정할 수 없다. 원문과 일정 내용에서 대응이 명확한 항목만 상태를 대조하고, 나머지는 관련 일정 후보와 `처리 확인 필요`로 표시한다. 초기 재설계에서 결정사항 관리 시스템을 추가할 필요는 없다.

루틴은 규칙, 계산한 예정 회차, 저장된 회차 처리 이력, 실제 일정의 상태를 각각 다룬다. 회차의 `created`는 일정 생성 상태이며 업무 완료가 아니다. `skipped`와 `acknowledged`도 완료 업무로 집계하지 않는다. 루틴에서 만들어진 일정과 예정 회차를 이중 집계하지 않는다. 반복 날짜 계산은 기존 `src/utils/routineRecurrence.ts`, `src/utils/routines.ts`를 재사용한다.

## 날짜와 업무 의미를 정하는 규칙

| 질문 표현 | 권장 기준 | 결과에 표시할 설명 |
| --- | --- | --- |
| 그날 일정 | `startAt`부터 유효한 `endAt`까지의 날짜 구간이 겹치는지 | 기간 일정 포함, Task ID 기준 한 건 |
| 그달 예정된 일의 완료율 | 예정 날짜 범위와 겹치는 일정의 현재 상태 | 완료 / 취소 제외 대상 수, 조회 시각의 상태 |
| 그달 완료한 일 | 현재 `DONE`인 일정의 `completedAt` | 완료일 기준. 완료일 미상 건수 별도 |
| 지연된 일 | 기존 `isTaskOverdue`와 일치하는 활성 일정 | 유효한 종료 시각이 있으면 그 시각, 없으면 시작 시각의 날짜가 오늘보다 이전인 미완료·보류 일정. 실제 제출 마감 의미와 구분 |
| 제출 마감 | 제출 종류 일정의 등록 시각 또는 본문에서 확인한 마감 표현 | 별도 마감 필드가 없으므로 등록된 제출 일정 기준임을 표시 |
| 지난 회의 결정 | 원문에 적힌 회의일·제목·결정 문단 | 노트 수정일을 회의일로 자동 간주하지 않음 |
| 최신 결정 | 원문에 명시된 변경·대체 관계 | 단순히 수정일이 늦다는 이유로 기존 결정을 폐기하지 않음 |

현재 Task의 `completedAt`은 재오픈 시 제거될 수 있다. 따라서 `완료한 일`은 현재 완료 상태의 완료 시각 기준으로 지원하고, 과거에 한 번 완료했다가 재오픈한 기록까지 복원하는 지표는 제공하지 않는다. 그러한 이력이 필요하면 상태 변경 이벤트 모델을 별도로 설계해야 한다.

9월 예정 업무가 취소 제외 12건이고 현재 완료 9건·미완료 2건·보류 1건이면 완료율은 75%다. 9월에 실제 완료한 건수는 이 숫자와 다를 수 있다. 완료일이 없는 예전 기록에 `updatedAt`을 몰래 대신 쓰지 않고 `완료일 미상`으로 분리한다. 미래 루틴의 예정일도 실제 등록 일정과 다른 표시를 사용한다.

## 답변 근거를 만드는 규칙

모든 근거는 이번 요청에서 실제 조회된 자료 묶음에서 발급한다. 노트 문단은 원문 ID·조회한 수정 시각·문단 위치·발췌, 일정은 ID·조회한 필드·수정 시각, 집계는 조건·분모·제외 사유를 보관한다. 모델은 이 근거 묶음의 키를 사용해 결론이나 결과 행에 출처를 붙인다.

앱은 키의 존재, 자료 유형, 허용 범위, 발췌가 조회 원문에 존재하는지, 계산값이 맞는지를 검사한다. 이 검사는 문장의 의미가 참임을 완전히 증명하지는 않는다. 인과관계·완료 판단·서로 다른 기록의 연결처럼 해석이 필요한 부분은 `AI 해석`으로 구분하고 확인 가능한 사실과 섞지 않는다.

상충하는 기록은 둘 다 보여 준다. `9월 22일 노트는 금요일 제출, 9월 25일 노트는 월요일 제출로 적혀 있어 최종 날짜를 확인할 수 없음`처럼 쓰고, 최근 자료라는 이유만으로 임의의 답을 정하지 않는다. 원문이 수정·삭제되면 기존 답변에 변화 표시를 붙이고 다시 확인하도록 한다.

확신도 92% 같은 근거 없는 숫자 대신 다음 상태를 사용한다.

| 상태 | 표시 예시 |
| --- | --- |
| 기록으로 확인 | 등록된 일정 3건을 확인했습니다 |
| AI 해석 | 두 노트를 함께 보면 검토 준비가 필요해 보입니다 |
| 정보 없음 | 이번 조회 범위에서는 관련 기록을 찾지 못했습니다 |
| 자료 부족 | 긴 노트의 일부를 아직 확인하지 못했습니다 |
| 상충 | 두 기록의 제출일이 달라 확인이 필요합니다 |

## 결과 화면과 결과물 표현

기본 화면은 **질문 입력 → 검색 결과 건수 → 일정·메모의 단일 목록**으로 구성한다. 요약 답변, 조회 조건 설명, 일치 이유와 후속 행동은 기본 검색 결과에 넣지 않는다. 제목·날짜·원문 발췌로 기록을 바로 찾고, 필요한 항목을 눌러 원문을 확인한다. 아래의 집계·요약·보고서 형식은 사용자가 해당 결과를 별도로 요청할 때의 확장안이다.

| 결과 | 화면 표현 | 복사와 저장 형식 |
| --- | --- | --- |
| 과거 출장 날짜 | 출장 일정과 출장 후 메모를 같은 목록에 표시. 제목·등록 기간 또는 수정일·원문 발췌 | 항목을 눌러 원문 확인 |
| 이전 교육 관련 노트 | 교육 일정과 메모를 같은 목록에 표시. 확인된 교육일과 수정일 구분 | 항목을 눌러 원문 확인 |
| 검색 결과 | 제목, 매칭 발췌, 프로젝트·날짜, 원문 열기 | 출처 목록을 포함한 짧은 Markdown |
| 일정 현황 | 일시, 제목, 상태, 종류, 원문 근거 표 | Markdown 표. 필요하면 이후 CSV 확장 |

| 실적 집계 | 주요 숫자와 프로젝트별 표. 비교가 필요할 때 작은 막대 차트 | 집계 기준·조회 시각·제외 건수가 붙은 표 |
| 변경 사항 | 변경 전후 표 또는 날짜순 타임라인 | 기준 스냅샷을 적은 변화 요약 |
| 보고서 | 제목, 요약, 완료·진행·확인 필요·다음 행동 | 편집 가능한 보고 노트 초안 |
| 다음 행동 | 일정 또는 체크리스트 초안 | 기존 편집·검토 화면에서 사용자가 저장 |

### 과거 일정과 교육 노트 결과 화면

2026년 10월 4일 사용자 피드백에 따라 목업을 단일 목록으로 수정했다. 검색창 아래에 결과 건수와 검색된 일정·메모를 쭉 보여 준다. 다른 후보와 관련 메모도 접지 않고 같은 목록에 둔다. 요약 답변, 해석한 조건, 일치 이유, 조회 정보, 후속 질문과 대화형 배치는 제거했다.

일정 행은 종류·등록 날짜 또는 기간·제목·원문 발췌를, 메모 행은 종류·수정일·제목·원문 발췌를 표시한다. 교육 메모에는 원문에서 확인한 교육일도 날짜 정보에 함께 표시한다. 일정의 등록 기간과 메모의 방문 내용은 각 기록에서 확인하며 화면이 별도의 방문 사실을 단정하지 않는다.

행을 누르면 PC에서는 목록 옆, 모바일에서는 목록 아래에 원문을 연다. 목록과 선택 항목을 유지하고 원문을 닫으면 해당 행으로 포커스를 돌린다. 제목과 발췌에서 검색어를 강조하며, 별도의 버튼과 설명 영역을 반복하지 않는다.

목업의 기록·날짜·원문은 합성 자료다. 두 예시 질문 전환과 목록의 원문 열기가 동작하며 실제 검색이나 사용자 데이터 조회를 수행하지 않는다.

### 별도로 요청한 집계와 요약

PC에서는 근거를 답변 옆 패널로, 모바일에서는 닫을 수 있는 시트로 연다. 답변은 유지하고 근거 번호를 누르면 해당 발췌를 강조한다. 원래 노트·일정 화면을 열더라도 돌아오면 질문과 결과를 복원한다. 키보드 접근과 포커스 복귀를 지원하고 표는 좁은 화면에서 행별 카드나 표 내부 스크롤로 읽을 수 있게 한다.

답변 예시는 다음과 같다. 수치와 제목은 합성 자료다.

```text
질문  다음 주 제출 일정 중 아직 안 끝난 것 보여줘
조건  2026.10.05–10.11 · 일정 · 제출 · 미완료와 보류

아직 끝나지 않은 제출 일정은 3건입니다.

10.05 18:00  교육 실적 제출       미완료  [근거 1]
10.08 18:00  사업 추진현황 제출   보류    [근거 2]
10.09 18:00  예산 요청서 제출     미완료  [근거 3]

등록된 제출 일정 기준입니다. 본문에 별도로 적힌 마감은 확인이 필요합니다.

[중요한 것만] [준비사항 확인] [노트 초안 만들기]
```

진행 표시는 내부 추론이 아닌 실제 작업 상태만 보여 준다. `조회 조건 확인`, `일정 38건 집계`, `연결 노트 3건 확인`, `요약 작성` 정도면 충분하다. 글자 수는 사용자에게 유용한 진행률이 아니므로 기본 화면에서 제거한다.

## 후속 질문과 결과 재사용

후속 질문은 이전 질문 문자열뿐 아니라 조회 조건, 선택한 항목 ID, 날짜 기준, 확인된 근거를 이어받는다. `그중 중요한 것만`은 이전 범위를 유지해 중요도 조건을 추가한다. `표로 바꿔줘`는 동일 자료를 다시 표현하고, `최신 상태로 다시 확인`은 새 조회를 실행한다. 범위를 바꾸면 이전 답변의 기준을 수정하지 않고 새 결과를 만든다.

질문 기록은 로컬 세션으로 보관한다. 권장 기본값은 최근 30개 세션, 원문 전체 중복 저장을 피한 질문·조건·결과·짧은 근거 발췌이며, 기록 끄기와 전체 삭제를 제공한다. 저장 기간과 용량 한도는 구현 시 측정해 확정한다. 예전 답변을 열면 당시 기준 시각을 표시하고 최신 답변처럼 취급하지 않는다.

`복사`는 본문·표·출처와 조회 조건을 담는다. `노트 초안 만들기`는 제목·본문·출처·기준 시각을 편집할 수 있게 하고 저장 후 원래 노트 기능을 이용한다. `일정 초안 만들기`는 대상·날짜·프로젝트·종류를 사용자가 검토한 뒤 저장하며 원문과의 연결을 유지한다. 답변에서 제안한 행동이라는 이유만으로 자동 등록하지 않는다.

AI 생성 노트가 이후 질문에서 원래 회의록처럼 쓰이지 않도록 원자료 출처와 생성 경위를 보존한다. 같은 질문에서 파생한 요약이 다시 원자료를 대체해 답변을 강화하지 않도록 원문 확인을 우선한다.

## 실패와 미확인 상태

| 상태 | 사용자가 보는 결과 | 다음 행동 |
| --- | --- | --- |
| AI 연결 없음 | 로컬 검색·조건 조회·수치는 사용 가능, AI 요약은 준비되지 않음 | 검색 결과 확인 또는 설정 이동 |
| 모호한 질문 | 필요한 조건 하나를 고르는 짧은 질문 | 선택 후 실행 |
| 자료 미발견 | 조회한 범위와 미발견 안내 | 키워드·기간 변경 또는 보관 자료 포함 |
| 일부 조회 | 읽은 범위와 남은 자료 표시, 전체 단정 제한 | 추가 조회 또는 범위 축소 |
| 중지 | 입력과 이전 결과 유지, 새 요청은 중단 상태 | 다시 실행 |
| 네트워크 오류 | 기존 결과 유지, 새 요청 실패 표시 | 같은 조건으로 재시도 |
| 출력 형식 실패 | AI 설명 해석 실패 표시, 검증된 로컬 결과는 유지 | 요약 재시도 |
| 원문 변경 | 당시 발췌와 변경 사실 표시 | 최신 자료로 다시 확인 |

상태 흐름은 `입력 → 해석 → 필요 시 확인 질문 → 조회 → 작성 → 검증 → 완료`로 둔다. 각 실행에 식별자를 부여해 취소·재시도 후 늦게 도착한 이전 응답이 최신 결과를 덮지 못하게 한다. 페이지 이동이나 새 질문을 시작해도 이미 완료한 결과는 남긴다.

## 데이터 범위와 보안

현재 앱은 승인된 빌드 프로필의 HTTPS 엔드포인트 검증, 쿠키 제외 요청, 요청·응답 크기 제한, 제한 시간, 동시 요청 제한을 갖고 있다. 질문 재설계에서도 `src/agent/llmClient.ts`를 공통 통신 계층으로 유지한다. 특정 서비스의 네이티브 도구 호출이나 출력 스키마 기능을 필수 조건으로 삼지 않는다.

전체 제목 카탈로그를 매 요청에 보내는 대신 질문·필요한 조건·관련 발췌·검증한 집계만 보낸다. 데이터가 로컬에 저장된다는 설명과 AI 사용 시 선택한 자료가 승인 서버로 전송된다는 설명을 구분한다. 프로젝트 범위와 보관 노트 포함 여부는 서버 전송 전에 앱에서 강제한다.

기본 검색 범위는 일반 질문에서는 활성·초안 노트, 일정은 질문의 상태 조건을 따르도록 권한다. `옛 기록`, `보관한 노트`를 물으면 보관 자료를 포함한다고 눈에 보이게 표시한다. 버전 이력과 일별 메모까지 묵시적으로 전송하지 않는다. 명시적으로 선택한 노트가 보관 상태면 해당 선택 범위를 우선해 보여 준다.

본문은 자료로 취급하며 그 안의 지시를 도구 명령이나 저장 명령으로 실행하지 않는다. 도구와 결과 스키마는 허용 목록으로 제한한다. 프롬프트에 자료를 분리해 적는 것만으로 모든 주입 공격을 막을 수는 없으므로 실행 권한 제한과 결과 검사를 함께 둔다. [OWASP 프롬프트 주입 예방 지침](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html).

질문 기록과 로그에는 API 키·인증 헤더·민감한 서버 오류 원문을 저장하지 않는다. 질문·발췌도 개인 업무자료이므로 로컬 기록 삭제와 사용량·진단 로그를 구분한다. 새로운 세션 저장소를 백업에 포함하려면 백업 형식과 구버전 가져오기 정책을 함께 정해야 한다. 초기 단계에서는 기존 백업을 변경하지 않고 질문 기록의 백업 제외를 명시하는 안을 권한다.

## 구현 단계와 완료 기준

예상 일정을 단정하기보다 아래 순서로 분리해 구현한다. 각 단계는 독립적으로 사용할 수 있어야 한다.

| 단계 | 주요 작업 | 완료 기준 |
| --- | --- | --- |
| 첫 단계 | 기억 단서의 분리와 관련 후보 검색, 과거 출장·교육 노트 찾기, 질문 전용 화면, 세션 상태, 범위 표시, 중지·재시도, 매칭 문단과 원문 근거 보기 | 사용자가 정확한 제목을 몰라도 관련 기록을 찾고, 출장 기간·교육일·수정일을 구분하며 원문을 열어도 답변이 유지됨 |
| 두 번째 단계 | 필요한 연결 자료 조회, 정확한 전체 집계, 노트 요약, 후속 질문, 복사·노트 초안·일정 초안 연결 | 완료 실적이 원자료와 일치하며 찾은 자료를 요약·저장·다음 행동으로 연결함 |
| 세 번째 단계 | 루틴·회차 조회, 비교 스냅샷, 원문 변경 알림, 일별 메모의 선택적 검색 | 실제 일정과 미래 회차를 구분하고 최신 상태 재조회가 정상 동작함 |
| 확장 단계 | 의미 검색, 상태 변경 이력, 고급 내보내기 | 기존 검색 대비 품질·비용 개선을 측정한 뒤 도입 |

첫 단계에서는 일반 검색과 정확한 조건 조회가 AI 서버 없이도 동작하도록 한다. AI 자연어 해석에 실패하면 사용자가 검색 단어와 프로젝트·기간·상태 필터를 수정해 같은 자료를 찾을 수 있게 한다. 새로운 화면만 먼저 만들고 기존의 단일 문자열 검색과 본문 앞부분만 읽는 한계를 그대로 두는 방식은 첫 단계 완료로 보지 않는다.

| 기존 파일과 구조 | 변경 또는 재사용 방향 |
| --- | --- |
| `src/components/AskDataModal.tsx` | 전용 화면으로 진입을 전환하고 필요하면 짧은 질문 진입창으로 축소 |
| `src/components/AppShell.tsx`, `src/routing.tsx`, `src/App.tsx` | 질문 화면 경로와 현재 위치 표시 추가 |
| `src/agent/qaAgent.ts` | 질문 해석·근거 기반 작성 흐름으로 분리 |
| `src/agent/agentTools.ts` | 다른 에이전트도 쓰므로 공유 도구의 기존 동작을 갑자기 변경하지 않고 QA용 조회 계층을 별도로 추가 |
| `src/agent/llmClient.ts`, `src/agent/agentUtils.ts` | 승인된 통신·제한·모델 호환성 유지, 형식 실패 처리 개선 |
| `src/models.ts`, `src/db.ts` | 조회 계획·결과·근거·세션 타입과 필요한 저장소·인덱스 설계 |
| `src/utils/taskTiming.ts`, `src/utils/taskStatus.ts` | 달력과 같은 기간 표시·지연·상태 의미 재사용 |
| `src/utils/routines.ts`, `src/utils/routineRecurrence.ts` | 루틴 계산을 별도로 재구현하지 않고 재사용 |
| `src/components/AiAssistantWorkspace.tsx` | 일정 초안 검토·동시성 검사 흐름과 연결 |

새 모듈의 권장 역할은 `questionPlan`의 해석 검증, `questionRepository`의 로컬 조회, `questionSearch`의 본문 검색, `questionEvidence`의 근거 검증, `QuestionWorkspace`의 화면과 세션 관리다. 이름과 파일 배치는 실제 구현 시 기존 구조에 맞춰 조정한다.

## 구현 검증 기준

다음은 향후 구현을 위한 수용 기준이며 이번 기획 작업에서 앱 기능 테스트를 통과했다는 뜻은 아니다.

| 검증 상황 | 기대 결과 |
| --- | --- |
| 질문의 업무 단서 두 개가 제목·본문에 떨어져 있음 | 질문 전체 문자열의 일치 여부에 의존하지 않고 함께 일치한 기록을 찾음 |
| 같은 업무의 과거 출장 3건 | 관련도와 출장 날짜를 보여 주고 하나를 임의로 확정하지 않음 |
| 과거 출장 일정이 취소·미완료·보류 상태 | 취소 기본 제외, 미완료·보류는 방문 여부 미확인으로 구분 |
| 예전 교육 노트를 가장 최근에 수정함 | 수정일을 교육일로 사용하지 않고 관련 행사일 기준으로 찾음 |
| 교육 노트는 있지만 행사일이 없음 | 노트를 반환하되 교육일 미확인 표시. 월이나 날짜를 만들어 내지 않음 |
| 단서 하나만 일치하는 후보 | 부분 일치와 빠진 조건을 표시, 전체 일치 답변으로 단정하지 않음 |
| 대상 일정 65건, 화면 15건 표시 | 총건수 65건으로 집계하며 다음 페이지 제공 |
| 9월 예정 대상 취소 제외 12건, 완료 9건 | 완료율 75%, 분모 12건 표시 |
| 완료일 없는 DONE 2건 | 실제 완료일 집계에서 미상 2건 표시. 수정일 대체 금지 |
| 검색 기간 전 시작해서 기간 안에 끝나는 일정 | 해당 기간 일정으로 포함, Task ID 기준 중복 집계 없음 |
| 본문 4,000자 뒤에 결정사항 | 해당 문단 검색·추가 조회 가능 |
| 보관 노트 | 기본 제외와 명시적 포함이 카탈로그·검색·상세에 동일 적용 |
| 존재하지만 이번 요청에서 조회하지 않은 ID를 AI가 인용 | 유효 근거로 인정하지 않음 |
| 서로 다른 날짜가 적힌 노트 두 개 | 상충 상태 표시, 임의의 최신 결정 생성 금지 |
| 루틴 created·skipped·acknowledged | 업무 DONE과 구분, 실제 일정과 회차 이중 집계 없음 |
| 다음 주→중요한 것만 후속 질문 | 기간·프로젝트 맥락 유지, 중요도 조건 추가 |
| 중지 직후 다시 질문 | 이전 응답이 새 결과를 덮지 않음 |

| AI 서버 없음 | 로컬 조회·집계 사용 가능, AI 설명 미제공 상태 명확 |

| 내부망·외부망·단일 HTML | 해당 빌드 프로필의 승인 주소와 CSP 유지 |

검색 품질은 합성 자료에 정답을 붙인 질문 세트로 평가한다. 일정 조회·집계는 정확한 기대값과 일치해야 한다. 노트 검색은 관련 자료 누락과 잘못 찾은 자료를 구분해 확인하고, 근거 발췌와 요약은 사람이 원문과 대조한다. 응답 시간은 로컬 조회와 AI 생성으로 나눠 측정해 개선 지점을 찾는다.

## 기존 기획과 이번 제안의 관계

2026년 9월 7일의 별도 질문 화면 시안과 `artifacts/check-question-concept.mjs`에는 기록, 근거 패널, 후속 질문, 초안 버튼이 이미 있다. 그러나 가상 응답 전환이고 저장·범위 필터는 실제 데이터 처리 기능이 아니다. `docs/updates/2026-09-14.md`, `2026-09-15.md`도 질문 전용 화면을 기획 단계로 설명한다.

이번 제안은 그 화면 방향을 이어받아 **전체 조회와 목록 제한의 분리, 날짜 기준의 구분, 실제 조회 근거 연결, 루틴의 상태 의미, 실패와 최신성 처리**를 구체화한다. 기존 시안에서 좋은 사용 흐름은 활용하고, 아직 구현되지 않은 검색·저장 기능을 완성된 기능으로 간주하지 않는다.

권장 시작점은 기억나는 단서로 과거 일정·노트를 찾고 원문을 바로 확인하는 경험이다. 질문 전용 화면과 단서를 조합하는 로컬 검색을 먼저 만들고, 그 위에 연결 조회, 집계, 대화 맥락, 결과물 저장을 순서대로 올리면 사용자가 무엇을 확인했고 어떤 자료로 만든 결과인지 계속 알 수 있다.
