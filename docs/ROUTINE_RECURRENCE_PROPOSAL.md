# 플래나이 나의 루틴 기능 분석과 반복 설정 확장

> 방향: **반복할 때마다 떠올려야 하는 일**을, **요일과 날짜를 몇 번 고르면 알아서 챙길 때를 알려주는 규칙**으로 만든다.

작성일: 2026-10-01 · 작업 범위: **기능 분석 + 모달 UI 시안 + 실제 앱 반영**

분석과 조작 가능한 시안을 만든 뒤, 사용자의 ‘이렇게 반영해줘’ 요청에 따라 한 화면 모달을 실제 앱에 적용했다. 일·주·월·연 규칙, 예정일 미리보기, 저장·처리·알림과 DB·백업 v7 전환을 연결했다. 아래의 확장 전 분석과 비교 시안은 설계 배경이며, 실제 적용한 정책은 이 문서의 안내·데이터 항목을 따른다.

## 한 줄 요약

`나의 루틴`에서 **주·월·년·일**을 고르고, 요일이나 날짜를 여러 개 선택하게 한다. 설정하는 동안 **읽기 쉬운 반복 문장과 다음 예정일**을 함께 보여주어, 사용자가 규칙을 저장하기 전에 결과를 확인할 수 있게 한다.

사용자 피드백에 따라 **루틴 목록에서 모달 폼을 열어 만들고, 저장하면 같은 목록으로 돌아오는 방식**을 적용했다. 한 화면 모달을 사용하며, `반복 규칙 → 알림과 연결`의 두 단계 방식은 비교 시안에만 남겨 두었다.

## 확장 전 루틴은 어떻게 동작했는가

현재 루틴은 등록 즉시 일정을 만드는 기능이 아니다. 반복 규칙을 보관하고, 안내일이 되면 사용자가 이번 회차의 일정을 만들거나 확인하도록 제안한다.

```text
루틴 등록
  → 예정일과 미리 안내할 날짜 계산
  → 안내일에 카드 표시
  → 일정 만들기 / 확인했어요 / 나중에 / 건너뛰기
  → 해당 회차의 처리 이력 저장
  → 다음 회차 안내
```

이 흐름은 유지할 가치가 있다. 자동으로 일정이 쌓이지 않으며, 일정을 만들기 전에 이번 회차의 제목·내용·시간을 수정할 수 있다. 루틴을 삭제해도 이미 만든 일정은 남는다.

### 현재 가능한 설정

| 항목 | 현재 동작 |
| --- | --- |
| 반복 간격 | 1~24개월, 12개월은 매년으로 표시 |
| 시작 기준 | 시작 월 |
| 예정일 | 한 달의 날짜 하나, 1~31일 |
| 없는 날짜 | 그 달의 마지막 날로 보정 |
| 미리 안내 | 당일~30일 전 |
| 안내 방식 | 일정 만들지 물어보기 / 알림만 받기 |
| 처리 | 일정 생성 / 확인 / 미루기 / 건너뛰기 |
| 규칙 수정 | 이미 만든 일정과 처리 이력 유지 |

월 단위 제한은 화면뿐 아니라 데이터 모델과 회차 ID에도 들어 있다. 화면에 요일 버튼만 추가해서 해결할 수 있는 변경은 아니다.

### 일반 일정의 반복과 나의 루틴은 역할이 다르다

일반 일정 추가 화면에는 이미 매일·매주·매월 반복이 있다. [AppDataContext.tsx:266](../src/context/AppDataContext.tsx#L266)의 `shiftIsoByPattern`으로 날짜를 이동하고, [924](../src/context/AppDataContext.tsx#L924)의 `recurrenceCount`에 따라 여러 일정을 한 번에 생성한다.

| 구분 | 일반 일정 반복 | 나의 루틴 |
| --- | --- | --- |
| 저장 시점 | 지정한 횟수의 일정을 한 번에 저장 | 규칙만 저장하고 안내할 때 이번 회차 처리 |
| 사용자의 선택 | 반복 일정 묶음 생성 시 확인 | 각 회차마다 일정 생성·확인·미루기·건너뛰기 |
| 생성 일정 | 반복 그룹과 순번을 갖는 일정 묶음 | `recurrencePattern: NONE`인 독립 일정 |
| 이력 연결 | 반복 그룹으로 구분 | 실제 루틴 회차와 `taskId`로 연결 |

공통 날짜 유틸 일부는 재사용할 수 있다. 하지만 일반 일정의 일괄 생성 함수를 그대로 연결하면 **안내를 받은 뒤 이번 회차 하나를 생성하는 루틴의 의미**가 바뀐다. 이번 확장은 루틴의 별도 날짜 계산과 회차 처리 구조를 유지하면서 넓히는 방향이다.

## 사용자가 쉽게 고를 수 있어야 하는 반복

자유도는 조건을 많이 입력하는 것보다, 자주 쓰는 규칙을 바로 만들 수 있을 때 체감된다.

| 하고 싶은 일 | 설정 방법 | 화면에 표시할 문장 예시 |
| --- | --- | --- |
| 매주 월·수·금 업무 정리 | 주 → 월·수·금 선택 | 매주 월요일·수요일·금요일 |
| 격주 월요일 점검 | 주 → 2주 간격 → 월요일 | 2주마다 월요일 |
| 매월 1일과 15일 정산 | 월 → 날짜 → 1·15 선택 | 매월 1일·15일 |
| 매월 마지막 날 취합 | 월 → 날짜 → 말일 선택 | 매월 말일 |
| 매월 마지막 금요일 보고 | 월 → 몇 번째 요일 → 마지막 → 금요일 | 매월 마지막 금요일 |
| 매월 둘째 화·목 정기 확인 | 월 → 몇 번째 요일 → 둘째 → 화·목 | 매월 둘째 화요일·목요일 |
| 3개월마다 마지막 날 점검 | 월 → 3개월 간격 → 말일 | 3개월마다 말일 |
| 매년 3월과 9월 15일 확인 | 년 → 3·9월 → 15일 | 매년 3월·9월 15일 |
| 하루 걸러 자료 확인 | 일 → 2일 간격 | 2일마다 |

`둘째 화요일·목요일`은 그 달의 **두 번째 화요일과 두 번째 목요일 각각**을 뜻한다. “그 달의 둘째 주에 있는 화·목”과 혼동하지 않도록 실제 예정일을 함께 보여준다.

`3개월마다 말일`은 시작 월을 기준으로 반복한다. 달력상 분기 말인 3·6·9·12월 말일을 지정하려면 연 반복에서 그 네 달과 말일을 선택한다.

### 선택한 종류에 맞는 항목만 보여주기

- **주:** 월~일 버튼을 여러 개 고른다. `평일`, `월·수·금`, `주말` 빠른 선택을 제공한다.
- **월:** `날짜`와 `몇 번째 요일` 중 하나를 고른다. 날짜는 1~31일과 `말일`, 요일은 첫째~다섯째·마지막과 여러 요일을 고른다.
- **년:** 반복할 월을 여러 개 고른 뒤 월 반복과 같은 날짜·요일 방식을 사용한다.
- **일:** 간격만 고른다. 매일, 2일마다, 3일마다를 같은 화면에서 설정한다.

29~31일을 선택했을 때만 `없는 날짜는 말일로 조정 / 그 달은 건너뛰기`를 보여준다. 다섯째 요일은 그 달에 없으면 건너뛴다는 설명을 바로 붙인다.

## 화면 구성

### 기본 흐름: 목록에서 만들고 목록으로 돌아오기

```text
나의 루틴 목록
  → [+ 루틴 추가]
  → [나의 루틴 추가] 모달 폼
  → [루틴 등록]
  → 같은 목록에 새 카드 표시

기존 카드의 [수정]
  → [루틴 수정] 모달 폼
  → [변경사항 저장]
  → 같은 목록의 카드 갱신
```

등록·수정이 끝나거나 취소해도 목록의 탐색 맥락을 유지한다. 별도 등록 페이지로 이동하지 않는다. 시안의 목록은 샘플 데이터이며, 모달 안의 저장 결과도 실제 앱에는 반영되지 않는다.

### 1. 한 화면 모달 — 기본 권장안

```text
나의 루틴 추가                             [닫기]
───────────────────────────────────────────────
어떤 일을 챙길까요?       [주간 업무 정리]

반복                     [매일] [매주✓] [매월] [매년]
                         [1] 주마다
반복할 요일              [월✓] [화] [수✓] [목] [금✓] [토] [일]
언제부터 시작할까요?     [2026-10-01]

이렇게 반복해요
매주 월요일·수요일·금요일
다음 예정일              10월 2일 · 5일 · 7일 · 9일 · 12일

▸ 알림과 연결            당일 안내 · 일정 만들지 물어보기
▸ 프로젝트·일정 설정
▸ 종료·예외 설정
▸ 함께 기억할 내용

───────────────────────────────────────────────
                             [취소] [루틴 등록]
```

모달 제목은 추가할 때 `나의 루틴 추가`, 수정할 때 `루틴 수정`이다. 이름, 반복 단위, 실제 요일·날짜, 시작일과 미리보기를 먼저 보여준다. 알림과 연결, 프로젝트·종류·일정 시간, 종료·예외, 메모는 접어서 폼을 짧게 유지한다. 접힌 알림 설정에도 현재 안내 방식과 시점을 짧게 표시한다.

넓은 화면에서는 미리보기를 오른쪽에 둘 수 있다. 모바일에서는 한 열로 배치하고 **반복 규칙 바로 아래**에 미리보기를 두어 결과를 확인하기 위해 추가 설정을 지나 내려갈 필요가 없게 한다. 요일·날짜의 선택 여부는 색과 체크 표시로 함께 표현한다. 모바일 터치 환경에서는 주요 선택 영역을 44px 이상으로 확보한다.

### 2. 두 단계 모달 — 비교안

```text
나의 루틴 추가                             [닫기]

1. 반복 규칙
   이름 / 반복 단위 / 요일·날짜 / 시작일 / 실제 예정일 미리보기
                         [취소] [다음: 알림 설정]

2. 알림과 연결
   미리 알림 / 안내 방식 / 프로젝트·일정 / 종료·예외 / 메모
                         [취소] [이전] [루틴 등록]
```

같은 모달 안에서 단계를 전환한다. 처음 등록하는 사용자가 반복 규칙에 집중하기 쉽고, 앞 단계로 돌아가도 입력은 유지한다. 자주 수정하는 사람에게는 이동 횟수가 늘어나므로 기본안과 비교한다. 두 단계에서도 최종 저장 후 같은 목록으로 돌아온다.

### 3. 닫기·포커스·스크롤 규칙

- 모달을 열면 루틴 이름 입력에 포커스를 둔다. `Tab`과 `Shift+Tab`은 모달 안의 보이는 입력·버튼만 순환한다.
- `닫기`, `취소`, `Escape`는 같은 닫기 동작을 사용한다. 수정한 입력이 있으면 **저장하지 않은 입력을 버릴지 확인**하고, 계속 작성하기를 선택하면 모달과 입력을 유지한다.
- 모달이 열린 동안 배경 목록은 `inert`로 두어 배경 클릭과 키보드 접근을 막는다. 닫으면 해제하고, 모달을 열었던 추가·수정 버튼으로 포커스를 돌린다.
- 저장 중에는 중복 저장과 닫기를 막고 처리 상태를 표시한다. 저장 오류는 폼 안에 안내하며 입력을 보존한다.
- 실제 앱에서는 기존 [TaskModal.tsx](../src/components/TaskModal.tsx)와 [useDialogFocus.ts](../src/hooks/useDialogFocus.ts)를 재사용한다. 배경 `inert`와 정리 동작을 함께 연결하고, **본문만 스크롤되며 헤더·취소/저장 푸터는 유지되는 모달**을 권장한다.

채팅에 표시되는 시안은 콘텐츠 높이에 맞춰 자동 확장된다. 이 시안에는 내부 스크롤 컨테이너나 뷰포트 고정 배치를 사용하지 않는다. 실제 앱 모달의 본문 스크롤과 헤더·푸터 고정은 후속 구현에서 별도로 검증한다.

### 4. 저장 전에 결과를 확인하기

미리보기는 반복 문장과 다음 3~5회 예정일, 각 예정일의 안내 날짜를 함께 보여준다. 시안은 주말 이동에 `날짜 조정` 표시를 붙이고, 말일 보정은 규칙 요약과 안내 문구로 설명한다. 실제 앱에서는 말일 보정도 해당 예정일에 표시하는 방향을 권장한다.

예를 들어 `매월 31일 → 없는 날짜는 말일`을 고르면 10월 31일 다음에 11월 30일이 보여야 한다. “매월 31일”이라는 문장만 보여주는 것보다 사용자가 결과를 빠르게 이해할 수 있다.

빈 요일·날짜 선택, 잘못된 시작일·종료일, 0 이하 간격은 미리보기 영역에 설명하고 등록을 막는다. 실제 앱에서는 해당 입력 아래에도 오류를 연결하는 방향을 권장한다. 알림 날짜가 이미 지났거나 미리 알림 기간이 다음 회차와 겹치면 미리보기에 이유를 보여준다.

### 5. 목록에서도 규칙을 읽을 수 있게 하기

루틴 카드에는 제목, 반복 문장, 다음 예정일, 안내 방식, 프로젝트를 보여준다. 자세한 메모와 처리 이력은 필요할 때 펼친다. 카드의 `수정`은 해당 규칙이 입력된 모달을 열고, 저장하면 같은 카드가 갱신되는 흐름으로 구성한다.

## 종료·예외 설정의 권장 정책

시안에는 다음 계산 정책을 적용했다. 실제 앱으로 옮길 때도 같은 문장과 같은 결과가 나와야 한다.

| 조건 | 시안의 동작 |
| --- | --- |
| 격주 기준 | 시작일이 속한 주의 월요일을 기준으로 2주 간격을 계산한다. 시작일 이전 날짜는 제외한다. |
| 없는 날짜: 말일 | 29~31일이 없는 달은 그 달 마지막 날로 조정한다. |
| 없는 날짜: 건너뛰기 | 그 달에는 해당 날짜의 회차를 만들지 않는다. |
| 다섯째 요일 | 다섯 번째 요일이 없는 달은 건너뛴다. `마지막`과 구분한다. |
| 주말 그대로 | 선택한 토·일에도 반복한다. |
| 주말 앞 평일 | 토·일을 앞선 금요일로 이동한다. |
| 주말 다음 평일 | 토·일을 다음 월요일로 이동한다. |
| 이동·보정 후 같은 날짜 | 같은 실제 날짜에 모인 예정은 한 번만 반복한다. |
| 명시한 제외 날짜 | 주말 이동이 끝난 실제 날짜에 적용한다. |
| 종료 날짜 | 종료일을 포함한다. 이동한 실제 예정일이 시작일~종료일 안에 있어야 한다. |
| 총 반복 횟수 | 시작일부터 이동·중복 병합·제외를 반영한 실제 회차 수를 센다. 미리보기에서 이미 지난 회차도 총수에 포함한다. |

주말 이동은 **토요일·일요일 처리**다. 금요일이 공휴일이어도 공휴일 여부를 자동 판단하지 않는다. 자동 공휴일 처리, 국가별 휴일 달력, 임의의 조건을 AND/OR로 섞는 자유형 규칙은 이번 시안 범위에 포함하지 않았다.

### 실제 앱에 적용한 알림과 미처리 회차 정책

확장 전 앱은 안내일이 지난 최신 회차 하나를 보여주며, 다음 회차의 안내일이 오면 미룬 이전 회차를 대체했다. 일·주 반복에서는 미뤄 둔 회차를 잃지 않도록 다음 정책을 적용했다.

- 신규 모달은 **매주 월·수·금 / 오늘 시작 / 당일 안내**로 열린다. 필요하면 단위·요일·미리 알림을 바꿀 수 있다.
- 다시 안내할 날이 된 명시적 미루기를 먼저 표시한다. 여러 건이면 다시 안내할 날짜, 원래 예정일 순서로 선택한다.
- 그다음 오늘을 포함한 **가장 최근 실제 예정일의 미처리 회차**를 표시하며, 미래 회차의 미리 안내보다 우선한다.
- 최근 실제 회차가 이미 처리되었으면 더 오래된 미처리 회차를 다시 꺼내지 않고 다음 미처리 예정일을 표시한다. 장기 미접속의 생략된 회차 수 표시는 추가하지 않았다.
- 아직 다시 안내할 날이 되지 않은 미루기는 보존한다. 다른 다음 회차가 있으면 그 회차를 안내하며, 반복 규칙이 끝나고 미룬 회차만 남으면 대기 상태로 표시한다. 규칙을 수정해도 명시적 미루기를 잃지 않는다.
- 처리 완료 여부는 실제 예정일로 판단한다. 규칙 변경 후 같은 예정일은 다시 제안하지 않으며, 다른 예정일은 새 회차로 취급한다.
- 루틴을 등록할 때 일정을 자동 생성하지 않는다. 안내 카드를 확인한 뒤 이번 회차의 일정을 만든다.

`매일 + 7일 전 안내`처럼 반복 간격보다 미리 안내 기간이 긴 경우에는 여러 회차의 안내가 겹친다. 후보 날짜를 많이 계산하는 것만으로 해결되지 않으며, 위의 우선순위와 미처리 정책이 먼저 필요하다.

## 데이터와 기존 사용자 호환성

### 월 전용 필드를 반복 규칙으로 바꾸기

실제 앱은 [RoutineRecurrence](../src/models.ts#L4)를 저장한다. 반복 종류를 바꿔도 선택했던 값을 유지하도록 공통 필드와 종류별 선택 배열을 함께 보관한다. 사용하지 않는 배열은 빈 배열도 허용하며, 현재 반복 종류에 필요한 선택은 입력·백업에서 검증한다.

```ts
type RoutineRecurrence = {
  frequency: "daily" | "weekly" | "monthly" | "yearly";
  interval: number;
  startDate: string;
  weekdays: number[]; // 월요일 1 ~ 일요일 7
  months: number[];
  monthMode: "dates" | "ordinal";
  monthDays: Array<number | "last">;
  ordinal: 1 | 2 | 3 | 4 | 5 | -1; // -1은 마지막
  ordinalWeekdays: number[];
  missingDate: "clamp" | "skip";
  weekend: "none" | "previous" | "next";
  excludeDates: string[];
  end: { type: "never" } | { type: "date"; date: string } | { type: "count"; count: number };
};
```

기존 제목·메모·프로젝트·일정 종류·일정 시간·안내 방식·활성 상태는 유지한다. 입력과 백업 가져오기에서 배열의 개수, 중복, 날짜 유효성, 요일·월 범위, 간격과 총수의 상한을 동일하게 검증해야 한다.

### 실제 예정일로 회차를 구분하기

기존 `루틴 ID:YYYY-MM`을 **`루틴 ID:YYYY-MM-DD`**로 바꾸었다. 같은 달의 1일·15일을 독립적으로 생성·확인·미루기·건너뛰기 처리할 수 있다. 주말 이동이나 말일 보정으로 같은 실제 날짜에 모이면 하나의 회차로 취급한다.

계산 결과에는 주말 이동 전 출처 날짜를 포함한다. 저장된 처리 이력의 예정일·상태·연결 일정·미루기·처리 시각은 그대로 보존하며, 현재 규칙으로 과거 이력을 다시 계산하지 않는다.

### 기존 데이터는 과거의 실제 기록을 기준으로 옮기기

1. 기존 `startMonth`는 그 달의 1일을 시작일로 변환한다.
2. 기존 `intervalMonths`와 `dayOfMonth`는 월 반복의 간격·날짜 하나로 변환한다. 없는 날짜는 기존처럼 말일 보정을 유지한다.
3. 기존 회차는 **이력에 저장된 `dueDate`**로 새 ID를 만든다. 현재 루틴의 수정된 규칙으로 과거 예정일을 다시 계산하지 않는다.
4. 과거 생성·확인·건너뛰기·미루기 상태, 연결 일정 ID, 처리 시각을 보존한다. 이미 완료한 일정도 그대로 둔다.
5. Dexie와 백업 버전을 올리고 기존 v4·v5·v6 백업을 읽는 경로를 유지한다. v4·v5에 루틴이 없으면 현재 전체 복원 정책대로 빈 루틴 목록을 가져온다.
6. 마이그레이션과 복원 직후 같은 회차가 다시 제안되거나 같은 일정이 중복 생성되지 않는지 검사한다.

DB·백업은 v7이며 이전 v4~v6 백업도 복원한다. 같은 실제 날짜로 변환되는 이력이 충돌하면 임의로 합치지 않고 전체 DB 업그레이드를 롤백해 원본을 보존한다. 새 v7 백업은 구버전 앱에서 복원할 수 없다.

### 알림과 저장 한도도 함께 확인하기

- 확장 알림은 안내일 오전 9시이며 `일정 기본 시간`과 별개다. 기존 시간 정책을 유지했다.
- 현재 알림에는 업무 제목·본문을 넣지 않고 ID와 시각만 전달한다. 새 규칙에서도 이 구조를 유지한다.
- 확장 알림은 실제 날짜 회차 ID를 사용한다. 같은 안내일의 과거 월간 전달 ID도 함께 확인해 이전 직후의 중복 전달을 막으며, 안내일을 바꾸면 새 알림을 허용한다.
- [background.js:239](../background.js#L239)에는 payload 500개, [252](../background.js#L252)에는 예약 알람 80개, [244](../background.js#L244)에는 전달 이력 2,000개 제한이 있다.
- [routines.ts:4](../src/utils/routines.ts#L4)의 루틴 500개·처리 이력 20,000개 한도는 일간 반복에서 더 빨리 찰 수 있다. 이력 보관 정책도 함께 검토한다.
- 현재 날짜·일정 생성은 장치의 로컬 시간을 사용한다. 일·주 간격은 달력 날짜로 계산하고, 다른 시간대와 일광절약시간에서도 기준이 흔들리지 않도록 검증한다.

## 단계별 구현 순서

### 1단계 — 화면과 처리 정책 확정

- **목록 → 한 화면 모달 → 저장 후 같은 목록**을 기본 흐름으로 적용하고, 두 단계 모달 비교안을 다듬는다.
- 오늘·기한 지난 회차·미룬 회차·미래 미리 안내의 우선순위를 정한다.
- 장기 미접속의 최신 회차와 생략 안내, 규칙 수정 후 처리 완료 회차, 종료 횟수의 의미를 정한다.
- 시안의 날짜 조정·중복 병합·명시 제외 정책을 앱 정책으로 확정한다.

### 2단계 — 데이터와 날짜 계산부터 통합

- 반복 규칙의 타입과 입력 검증, 실제 날짜 기반 회차 ID를 추가한다.
- 기존 DB와 v6 백업을 변환하고 과거 이력·생성 일정 보존을 확인한다.
- 복수 요일·날짜, 격주, 월말, 윤년, 종료·예외를 앱의 날짜 계산에 통합한다.
- 일·주 간격과 DST, 연말·월말 경계, 시작일·종료일의 포함 여부를 검증한다.

### 3단계 — 등록·편집·목록 연결

- 선택한 반복 종류의 입력만 보여주고 실제 다음 예정일을 미리보기한다.
- 기존 루틴을 편집했을 때 동일한 규칙과 예정일이 유지되는지 확인한다.
- 목록과 알림 카드에서도 같은 반복 문장을 사용한다.
- `TaskModal`·`useDialogFocus`를 재사용해 초기 포커스, Tab 순환, Escape, 입력 폐기 확인과 트리거 포커스 복귀를 연결한다.
- 배경 `inert`, 본문 스크롤, 헤더·푸터 유지, 오류 안내, 터치 영역, 모바일 한 열과 규칙 바로 아래 미리보기를 확인한다.

### 4단계 — 처리·알림·백업 회귀 검증

- 한 달 여러 회차를 각각 생성·확인·미루기·건너뛰기 처리한다.
- 여러 탭의 동시 요청에서도 한 회차의 일정이 한 번만 생성되게 한다.
- 규칙 변경 중인 오래된 초안 거부, 삭제 후 생성 일정 유지, 백업 복원 후 재제안 방지를 확인한다.
- 확장 알람 ID 전환, 중복 전달 방지, 앱 재시작·날짜 변경·알림 해제를 확인한다.
- 검증을 마친 뒤 앱 빌드와 배포 산출물에 반영한다.

## 성공 기준

- 사용자가 설명서를 읽지 않고 `매주 월·수·금`이나 `매월 1일·15일`을 등록할 수 있는가.
- 반복 문장과 실제 예정일을 보고 없는 날짜·격주·마지막 요일의 결과를 이해하는가.
- 자주 쓰는 규칙은 짧은 화면에서 끝나고, 예외가 필요한 사람만 추가 설정을 여는가.
- 목록에서 모달로 등록·수정한 뒤 같은 목록과 원래 버튼으로 자연스럽게 돌아오는가.
- 규칙 변경과 백업 복원 후에도 이미 처리한 회차와 일정이 보존되는가.
- 고빈도 루틴에서 미룬 일을 잃거나 같은 회차를 중복 생성하지 않는가.

`나의 루틴`의 중심은 사용자가 반복 조건을 정확히 입력하는 수고를 줄이는 데 있다. **직접 고르는 요일·날짜와 실제 다음 예정일**을 함께 보여주는 화면을 먼저 확정하고, 그 결과를 저장·처리·알림·백업까지 일관되게 이어가는 순서로 구현한다.

## 실제 앱 반영 결과와 검증

- [RoutineEditor.tsx](../src/components/RoutineEditor.tsx)에서 한 화면 모달을 사용한다. 데스크톱은 조건과 미리보기 두 열, 모바일은 규칙 바로 아래 미리보기 한 열이며, 본문만 스크롤하고 하단 취소·저장 버튼은 유지한다. 초기 포커스·Tab 순환·Escape·입력 폐기 확인·목록 버튼으로 포커스 복귀를 지원한다.
- 매일·매주·매월·매년, 간격 1~365, 다중 요일·날짜·월, 말일·첫째~다섯째·마지막 요일, 없는 날짜·주말·제외일·종료일·총수 조건을 지원한다. 날짜 범위는 2000~2100년, 총수는 최대 10,000회, 제외일은 최대 1,000개다.
- 미리보기는 실제 현재 날짜부터 다음 미처리 5회를 보여주며 오늘도 포함한다. 제목을 입력하기 전에도 계산하고, 편집 시 처리한 예정일은 제외한다. 주말 이동과 말일 보정에 날짜 조정 표시를 붙인다.
- 종료한 루틴은 별도 필터와 종료 상태로 관리한다. 명시적 미루기가 남아 있으면 규칙이 끝나도 그 회차를 보존한다. 생성 일정은 별도의 단일 일정이며 루틴 삭제·규칙 수정으로 이미 만든 일정을 바꾸지 않는다.
- `npm test` 전체, 날짜·경계 조건 55개, 실제 IndexedDB v6→v7 이전·롤백·v6 백업 복원·원자적 생성·오래된 편집 거부가 통과했다. 실제 앱 UI와 확장 알림의 네 회귀 스크립트, 320·390px 배치, 중복 제출, 모달 폐기·포커스, 종료·이력 미리보기를 검증했다.
- 독립적으로 하루씩 달력을 훑는 기준과 1,645개 조합·3,290개 결과를 비교해 불일치가 없었다. [검증 결과](../artifacts/routine-design-2026-10-01/review-differential.json)에 성능 측정도 보관했다. 기본 월간 500개는 약 4ms, 단순 일간 총수 10,000회 규칙 500개는 약 3ms였다. 주말 이동·병합까지 포함한 최대 총수 규칙 500개의 첫 계산은 약 3.3초로, 이 극단 조합의 성능 한계는 남아 있다.
- 변경 파일 대상 ESLint, 내부망·외부망·단일 HTML 빌드, HTML 무결성 검사와 두 ZIP의 전체 파일 바이트 일치 검증을 완료했다.
